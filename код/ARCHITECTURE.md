# ARCHITECTURE — neironka-poster

**Контракт для разработки в нескольких чатах.** Прежде чем менять схему БД, статусы аккаунтов или добавлять движок — сверься с этим файлом. Дрейф схемы (когда 4 чата пишут в одну таблицу несогласованно) — главный риск; этот документ его гасит.

---

## 0. Главное: чат ≠ модель ≠ сервис

- **Чаты** (ЛОГГЕР / ПОСТИНГ / ДЕЖУРСТВО / РАДАР) — это **рабочие столы разработки** (Claude-сессии). Они НЕ деплоятся и НЕ живут в проде.
- **Прод** — это Node-процессы на Railway из **одного репозитория**.
- **«Слаженная работа» ролей = общая БД Postgres**, а не связь чатов. Никто никому не «выдаёт» данные — все пишут/читают одни таблицы.

Разработку ведём в разных чатах (фокус по подсистеме), но **один репозиторий + этот контракт**.

---

## 1. Топология прода (Railway)

Один Docker-образ, ветвление по `ROLE` (`src/index.ts`):

| Сервис | ROLE | Что крутит |
|---|---|---|
| **web** | (пусто) | Express-панель (`api.ts`) + `worker.ts` (автопостинг, авто-релогин, сессии, прогрев, радар-скан) |
| **ig-worker** | `engines` | `engines.cjs` → супервизор движков: `duty_safe`, `backlog_safe`, `validate_safe`, **`queue_supervisor` (комментинг)**, **`newpost_watch`** |
| **postgres** | — | БД = шина между всеми |
| worker/ (опц.) | — | python-ферма по кукам (отдельный сервис, Root=worker) |

**Почему разнесено:** два `startWorker()` на одну базу = гонки за GoLogin-профили. Автопостинг — в web, комментинг — в ig-worker.

### Деплой
```bash
npm run deploy          # = predeploy(tsc) && railway up --service web
npm run deploy:engines  # railway up --service ig-worker
```
`predeploy` прогоняет `tsc --noEmit` — битые типы не уедут в прод. `start` = `npm run migrate && npm start` (migrate идемпотентно гоняет `schema.sql`, build-шага нет — tsx в рантайме).

| Роль (чат) | В проде | Ключевые файлы |

| **ПОСТИНГ** | web `maybePublish` (посты) + ig-worker `queue_supervisor→smartrun→vcomment` (комменты) | `worker.ts`, `queue_supervisor.cjs`, `smartrun.cjs`, `vcomment.cjs` |

## 3. State-machine аккаунта (СЕРДЦЕ КОНТРАКТА)

Статус в 3 колонках `accounts`:
- **`session_status`**: `live` | `dead` — жива ли IG-сессия
- **`ig_status`**: `login_ok` | `challenge` | `suspended` | `captcha` | `bad_login` | `2fa_cooldown` | `restricted` | `profile_lost` — почему умер
- **`status`**: `warming` | `paused` — стоп-флаг (paused = терминально, воркер не трогает)

### Кто ПИШЕТ «мёртв» (все → `session_status='dead'`, +уточнение)
| Триггер | Ставит | Где |
|---|---|---|
| Капча в комментинге | `dead + challenge + paused` | `vcomment.cjs recordCaptcha` (+`captcha_dead`) |
| «Нельзя делиться ссылками» | `ig_status='restricted'` | `vcomment.cjs recordShareRestrict` (+`share_restricted`) |
| Провал входа (прогрев/релогин) | `challenge`/`bad_login`/`2fa_cooldown` + paused | `worker.ts` maybeWarmup/maybeRelogin/reloginInline |
| Суспенд-детект | `suspended + paused + dead` | `suspendcheck*.cjs`, vision `reportFailureScreen` |
| **IG сказал «ограничение»** (в публикации) | `paused + health_state='restricted'` (ig_status НЕ трогаем) | **`postguard.cjs noteFailure`** — с ПЕРВОГО провала, не по счётчику |
| 3 провала публикации за 3ч | `paused` + `health_note` | `postguard.cjs noteFailure` |
| REST-чек куки сдох | `dead` (храповик: dead→live только реальным входом) | `worker.ts maybeSessions` |

### Кто ЧИТАЕТ и ПОДНИМАЕТ (авто, 24/7 на web)
| Механизм | Частота | Берёт |
|---|---|---|
| **`maybeRelogin`** | **20 мин** | `session_status<>'live'` + есть пароль, ≤10 акков, пул 3, кулдаун 1ч (2fa — 4ч) |
| **`reloginInline`** | **мгновенно** | разлогин пойман прямо в работе (seed/тишина) |
| **`maybeSilenceWatch`** | 45 мин | 1 «молчун» (session_checked_at >8ч) — браузерная перепроверка |
| **egress-гейт** (`ensureEgress`) | перед каждой работой | после `connect` в seed/duty/reply/relogin/warmup: мёртвый прокси (`proxy_status='dead'`) → в работу НЕ пускаем (гасит вериф-номера). Троттл: свежий `ok`<3д — probe не жжём |
| **`maybeFixProxy`** | 10 мин | `ig_proxy IS NULL` / `proxy_status` in (dead,mismatch) → `drawProxy` из `proxy_pool` → **`setProfileProxy` (дожать IP в облачный профиль!)** → сброс egress → re-verify. Корень «релогин 0» = IP не дожат в профиль |
| **`maybeReconcileProfiles`** | 1 ч | порт `glreconcile`: pid акка пропал из GoLogin → `ig_status='profile_lost'`, `pid=NULL`, `status` ОСТАётся warming. Абортит проход при неполном списке (ложный lost) |
| **`maybeRebuildLostProfiles`** | 15 мин | `profile_lost` (ставят reconcile ИЛИ ПОСТИНГ/smartrun) → `createCloudProfile`+`setProfileProxy`+`ensureEgress`+вход. Кап `PROFILE_REBUILD_MAX`, гардрейл `gologinHealth().down`, персист pid ДО connect |
| **`maybeSoftblockRecover`** | 30 мин | `bad_login` + `blocked_at`>2ч → свежий sticky из `proxy_pool` + вход паролём+2FA (дежурная полоса) |
| **`maybeCleanupDead`** | **6 ч** | ВАЛИДИРУЕТ браузером+аналитиком ПЕРЕД сносом: сироты-профили удалённых акков (тут `deleted_at` уже стоит, замки не нужны); терминальные (suspended/captcha >24ч) — подтвердил vision → корзина+снос профиля, «восстановимо» → вернул под релогин. **Два замка поверх валидации** (см. ниже) |
| **`maybeReplaceBlocked`** | 20 мин | `paused` + терминальный → снос профиля + завод замены из очереди. **Те же два замка** |
| **`POST /api/accounts/revive`** | по сигналу | внешний рычаг: снимает паузу, чистит fails → maybeRelogin подхватит |
| `captchaSweep` / `liftShareRestricted` | каждую волну | ig-worker `queue_supervisor`: снос капча-акков; возврат share-restricted через 30д |

### Два замка автосноса (06.08) — единые для `maybeReplaceBlocked` и `maybeCleanupDead`
Обе функции сносят GoLogin-профиль вместе с акком, то есть теряются прогрев и вся история, обратно не поднять. Поэтому в SELECT кандидатов у обеих стоит:
1. `coalesce(health_state,'') <> 'keep'` — владелец сказал «не удалять, ждём».
2. `NOT EXISTS (SELECT 1 FROM posts p WHERE p.account_id=a.id AND p.status='published')` — акк, у которого есть НАШИ публикации, автомат не сносит никогда, такой случай разбирает человек.

Зачем замок №2, если есть №1: `keep` кто-то должен успеть поставить руками. 06.08 так почти потеряли `darya.smirnova13` (16 публикаций, 3618 просмотров) — она поймала чекпоинт после входа с телефона, спас только ручной `keep`. Валидация браузером+vision в `maybeCleanupDead` от этого не страхует: чекпоинт живого акка выглядит как терминальный экран.

> ⛔ **ПРОВЕРЕНО 06.08 ФАКТОМ: В ПРОДЕ ЭТИХ ЗАМКОВ НЕТ.** Оба замка написаны, но лежат в **незакоммиченном** `src/worker.ts`; на Railway работает сборка из HEAD, где слова `keep` нет вовсе (`git show HEAD:src/worker.ts | grep keep` → 0), а SELECT `maybeReplaceBlocked` состоит ровно из `status='paused' AND ig_status IN ('challenge','suspended','captcha')`. Итог одного дня: снесены `zander33579`, `nico838020`, `devan47310`, `cason51726` — **все четыре с `health_state='keep'`** — плюс `kasey37750`, `jerimiah56338`, `mark755876`, `nick95738`. Пока `src/worker.ts` не закоммичен и не задеплоен, `status='paused'` на терминальном акке = снос вместе с профилем GoLogin в течение 20 минут, до 3 акков за цикл. Экстренное гашение — `AUTO_REPLACE_OFF=1` на web. Уборщик (§9) проверяет это ФАКТОМ каждый круг (проверка C0) и, пока замок не работает, паузу по инварианту 1 НЕ ставит.

Приказ на снос (обе функции, один флаг): **`REPLACE_KILL_PUBLISHED=1`**. Сироты-профили в `maybeCleanupDead` (ветка `deleted_at IS NOT NULL`) под замки не попадают: акк уже в корзине, сносится только висящий профиль.

### Дежурный резерв слотов (lock.ts)
Из ~10 облачных сессий GoLogin-аккаунта дежурству (релогин/подъём/сторож/софт-блок/cleanup — через `withLoginSlot`) зарезервировано `DUTY_RESERVE` (по умолч. 3); регулярные задачи (комментинг/радар/прогрев — `withBrowserLock`) берут не больше `CLOUD_TOTAL−reserve`. **Тревога** (`enterAlarm`, при массовой смерти в maybeSessions) поднимает резерв 3→5 на 30 мин. `blocked_at` — момент постановки блок-статуса (триггер `set_blocked_at`), НЕ сбивается чеками/revive; по нему честно мерим «2ч после софт-блока».

### Предохранитель публикации (`postguard.cjs`) — ЕДИНАЯ точка допуска
Задачу `local_jobs.mode='igpost'` создают несколько источников (`postdaemon.cjs`, `blast_one_each.cjs`, ретрай в постдемоне, `kasey_daily.cjs`, `tmp_blast6.cjs`, `api.ts /promo/publish/:id`, `worker.ts maybePushPromo`). До 06.08 у каждого был свой набор проверок или их отсутствие, из-за этого `cherry.mood59` получил 25 заходов ночью и 42 провала за час на аккаунте с ограничением от IG.

`canPost(slugOrId) → {ok, hard, code, reason}` — ОДНО решение для всех: `status`/`health_state`, `ig_status`/`session_status`, серия провалов (2 за 3ч) и тишина 30 мин после провала, живая igpost-задача, дневной лимит с личным `posts_per_day`, интервал, кулдаун 12ч после оформления. Стадия `'run'` — финальный гейт в `igpost2.cjs` ДО открытия окна Orbita (вход не тратится). `hard=true` (безопасность акка) не обходится ничем; `hard=false` (темп) снимается `POSTGUARD_PACING_OFF=1`.

`noteFailure()` — единственная точка «провал публикации»: зовётся из `localrunner.cjs` по исходу задачи, считает провалы, снимает акк с постинга и шлёт алерт в ТГ на 1-м и пороговом провале. Новый источник задач ОБЯЗАН звать `canPost` до INSERT; на уровне базы это подпирает `uq_local_jobs_igpost_slug_live`.

### ⚠️ Инварианты (НЕ нарушать при доработке)
1. Пометил акк капчей → **обязательно `status='paused'`** (иначе maybeReplaceBlocked не заменит, а maybeRelogin жжёт попытки).
2. `dead→live` **только реальным входом** (храповик maybeSessions) — REST-чек куки не воскрешает.
3. `ig_status='restricted'` акки **исключены из всех пулов** (share-restricted не постит) — снимаются авто через 30 дней.
5. **`profile_lost` HANDSHAKE:** ПОСТИНГ/smartrun (write-side) при no_connect потерянного профиля ставит `ig_status='profile_lost'`, `session_status='dead'`, **`status` ОСТАётся `warming` (НЕ paused)**. web (read-side) `maybeReconcileProfiles` ставит то же по сверке БД↔GoLogin. web `maybeRebuildLostProfiles` заводит профиль заново. `maybeReplaceBlocked`/автозавод из очереди profile_lost НЕ трогают (иначе 2-й профиль = утечка слота — в т.ч. api.ts:610/189, TODO вне worker.ts). `blocked_at` для profile_lost НЕ ставится (не в триггере).
6. **Egress перед работой:** `proxy_status='dead'` ставится ТОЛЬКО реальным замером (`ensureEgress`/`probeEgress`); свежий акк = `unknown` и в работу проходит. НЕ фильтровать пулы по `unknown`/NULL egress — заморозит весь свежий флот.
4. Куки-акки без пароля авто-подъёма НЕ имеют — только руками. **Куки-акк с ПОДТВЕРЖДЁННО неверным паролём (`bad_creds`) = потерян** (кука сдохла + пароль мусорный) → сносим везде (профиль+`deleted_at`+прокси в пул); `need_login` ≠ `bad_creds` (не удалять на ambiguous).
8. **Задачу публикации ставим ТОЛЬКО через `postguard.canPost`.** Свои проверки «болен ли акк / сколько провалов / занят ли» по месту НЕ заводить — расхождение наборов проверок и есть причина инцидента 06.08. **Ни один автомат не сносит акк с нашими публикациями или с `health_state='keep'`** — это `maybeReplaceBlocked` И `maybeCleanupDead`, оба замка описаны в §3; приказ на снос — `REPLACE_KILL_PUBLISHED=1`. Новую ветку автосноса заводишь → те же два условия в SELECT, иначе дыра открывается заново.
9. **`health_state='hidden'` («профиль спрятан снаружи») — ФАКТ, А НЕ ПРИГОВОР (10.08).** Публичная ручка `users/web_profile_info` отдаёт на часть наших акков HTTP 200 с голым `{"status":"ok"}` — БЕЗ ключа `data`. Калибровка: выдуманный ник даёт честный 404 (8 из 8), контрольные живые акки через те же прокси в те же минуты отдаются, а эти — ни разу за 8-12 попыток с 7-10 разных IP. Значит ник занят, аккаунт есть, но анониму профиль не показывают (ограничение или чекпоинт; наш `damari1735` в капче отвечает так же, и его рилс отдаёт 302 на логин). Раньше это состояние не различал НИКТО: `accheck` писал «сбой», `modelduty` — `unknown`, `checkposted` — «не прочитал (код 200)», и акк оставался `health_state='ok'`, уходя в работу публиковать в пустоту (все 8 разобранных стояли `warming`+`ok`).
   **Правила обращения:**
   - вердикт ставится ТОЛЬКО после подтверждения с **нескольких РАЗНЫХ egress** (`igprofile.probe`, по умолчанию 2 канала из 4 попыток). Ответ «Please wait a few minutes» (HTTP 401) и 429 в счёт не идут вообще — это лимит НАШЕГО айпи, а не факт про акк. Не подтвердилось → «вердикта нет», в базу ничего;
   - **`hidden` ≠ бан.** Анонимно временный чекпоинт от насмерть отключённого акка не отличить, поэтому: ни `paused`, ни `session_status='dead'`, ни `ig_status`, и **никакого автосноса/автозамены по этой метке** — цена ошибки максимальная (снос уносит профиль GoLogin навсегда, см. замки выше);
   - метка НЕ гейт постинга (в `BLOCK_HEALTH` не входит) и снимается сама, как только профиль снова отдаётся анониму — иначе она самозапечатывается, как ложный `banned` до 07.08;
   - проверка входом — отдельная фаза: `modelduty` ступень 2 (куки-реанимация, БЕЗ ввода пароля) показывает экраном, чекпоинт это или бан.
   **Разбор ответа и правило подтверждения живут в ОДНОМ месте — `igprofile.cjs`** (`classify` / `probe` / `PROTECTED` / `isThrottle`); читатели (`accheck`, `modelduty`, `checkposted`, `accjanitor`, `scanpub`, `hiddenscan`) своих копий не заводят: пять разъехавшихся копий этого разбора уже стоили ложных банов. Анонимные чеки читают ферму через пул прокси (`/tmp/px`, `proxy_pool`), потому что с нашего айпи после сотни запросов весь прогон превращается в «сбой» и слепое пятно возвращается. Никакой внешний чек не перетирает `health_state` из `igprofile.PROTECTED` (там же `keep` — замок автосноса).
7. **Кулдаун авто-входа считаем по `relogin_try_at`, НЕ по `session_checked_at`.** `session_checked_at` бампают фоновые чеки (maybeSessions/maybeSilenceWatch ~30 мин) → гейт кулдауна (2fa_cooldown 4ч / прочие 1ч) по нему НИКОГДА не дозревал → релогин не брал акки, 2FA висели вечно. `relogin_try_at` бампается ТОЛЬКО при реальной попытке входа (maybeRelogin все 4 ветки + api.ts loginAccountOnce); фоновые чеки его не трогают; revive сбрасывает в NULL (мгновенный подхват). НЕ возвращать кулдаун входа на `session_checked_at`.

## 4. DB-шина (общие таблицы)

**Конфиг/статус:** `accounts` (центр), `account_groups` (per-group `gologin_token`, `watchdog`, seed-настройки).

**Радар:** `radar_posts` (очередь; `queued_at`=«В РАБОТЕ»), `radar_creators` (авторы под слежкой).

**Комментинг (теперь в `schema.sql`, migrate владеет):**
`post_answered` (дедуп), `account_run_stats` (статистика+brand), `captcha_dead`, `share_restricted`, `post_restricted`, `account_post_done` (no-repeat), `brand_posted` (кап бренда).

**Прокси-пул:** `proxy_pool` (`proxy, country, status=free|assigned|dead, assigned_slug`) — запас sticky-прокси, восстановление берёт свободный мгновенно (у ClickIP нет API → создаём пачкой из браузера). `accounts.blocked_at` — время постановки блок-статуса (авто-триггер). `accounts.relogin_try_at` — время ПОСЛЕДНЕЙ реальной попытки входа (гейт кулдауна релогина; см. инвариант 7), НЕ путать с `session_checked_at` (последний бампают фоновые чеки).

**Правило:** новую общую таблицу — СНАЧАЛА в `schema.sql`, потом код. `CREATE TABLE IF NOT EXISTS` из скриптов — только временно, обязательно перенести в схему.

## 5. Env-флаги (гашение без передеплоя)

| Флаг | Сервис | Эффект |
|---|---|---|
| `WORK_QUEUE_OFF=1` | web | выключить `maybeWorkQueue` — **обязательно если commenter-движок в ig-worker включён** (анти-дубль) |
| `COMMENTER_OFF=1` | ig-worker | выключить `queue_supervisor` |
| `NEWPOST_OFF=1` | ig-worker | выключить «комментим первыми» |
| `DUTY_OFF` / `BACKLOG_OFF` / `VALIDATE_OFF` | ig-worker | гасить движки дежурства/бэклога/валидатора |
| `AUTO_REPLACE_OFF=1` | web | выключить авто-снос+замену |
| `REPLACE_KILL_PUBLISHED=1` | web | приказ на снос: снять замок «есть наши публикации» у `maybeReplaceBlocked` И `maybeCleanupDead` (`health_state='keep'` он НЕ снимает) |
| `CONC_OVERRIDE`, `SHARE_RESTRICT_DAYS`, `SUPERVISOR_DIR` | ig-worker | настройки конвейера |

## 8. Бюджет слотов GoLogin (15) — глобальный семафор

Слотов GoLogin **15**. Раньше кап был по env НА ПРОЦЕСС (web и ig-worker — разные процессы), сумма не координировалась → overcommit → `no_connect` (co-причина «релогин висит на 0»). Теперь единый счётчик в БД (`gologin_slots` + `claim_gologin_slot`/`release_gologin_slot`, advisory-lock, TTL 15 мин на протухшие). Открытие профиля идёт через `gologin.ts connect(opts.pool)` → claim ДО открытия, `disconnect` → release (close-after-use). Нет слота → `connect` бросает, вызывающий скипает (бэкпрешер, не крэш).

| Пул | Кап | Кто потребляет |
|---|---|---|
| **commenting** | 7 | ig-worker `queue_supervisor`/`vcomment` |
| **patrol** | 3 | ig-worker `duty_safe`/`backlog_safe`/`newpost_watch` + web `dutyTick` |
| **logger** | 3 (до **5** в экстренке) | web `worker.ts`: relogin, warmup, seed, silence, softblock, fixproxy, rebuild, publish |
| ИТОГО | ≤15 (база 13, пик 15) | жёсткий `p_total_cap=15` в функции |

**Экстренный burst логгера 3→5:** только когда сработал `relogin-watchdog` (`reloginWatchAlerted` = есть подъёмные акки при 0 успехов входа). Реализовано `loggerCap()` — logger-claim'ы передают `poolCap=loggerCap()`. Лишние 2 берутся из общего запаса (15−13), total не превышает 15.

**Правила для ВСЕХ процессов:** любой открывающий облачный профиль (web/ig-worker, TS или .cjs) обязан `claim_gologin_slot(pool, holder, pool_cap, 15)` перед и `release_gologin_slot(id)` после. Свои счётчики НЕ заводить. Теги пулов согласованы: commenting=ПОСТИНГ, patrol=ДЕЖУРСТВО, logger=ЛОГГЕР(web). Env-капы (`GOLOGIN_CONCURRENCY`, `LOGIN_CONCURRENCY`) — лишь ЛОКАЛЬНЫЙ throttle внутри процесса, истина = семафор в БД.

### Инварианты уборщика (НЕ нарушать при доработке)

1. **Диагностика — только анонимно, снаружи.** Ни одной куки, ни одного окна, ни одного входа: чтение публичного профиля обычным curl. Вход в акк это отдельная фаза и отдельный флаг.
2. **Вход только под конкретную починку и в пределах порогов:** `JANITOR_LOGIN=1` (по умолчанию ВЫКЛ), ≤`JANITOR_LOGIN_MAX` (2) заходов за круг, пауза `JANITOR_LOGIN_GAP_MIN` (20 мин), один акк не чаще раза в `JANITOR_ACC_COOLDOWN_H` (24 ч), тишина `JANITOR_POST_QUIET_MIN` (60 мин) после публикации. Никогда: при живой `igpost`-задаче по акку, при занятом `/tmp/genposts.lock`, на `paused`/`trash`, на `banned`/`restricted`/`needs_human_verify`, при мёртвой сессии.
3. **Не удаляет ничего и не даёт удалить.** Ни аккаунтов, ни постов, ни профилей GoLogin. Не делает `pkill` по Orbita/gologin (снесёт окна начальника и чужих чатов). Свои процессы гасит по имени скрипта, окна закрывает через `closeone.cjs`.
   **⚠ Урок приёмки 06.08 (ценой трёх акков).** Первый прогон с починкой поставил `paused` семи забаненным аккам по инварианту 1 — и через 20 минут `maybeReplaceBlocked` снёс три из них вместе с профилями (`jerimiah56338`, `mark755876`, `nick95738`). Формально это контракт (paused + терминальный = замена), но приказ «аккаунты не удалять» прямее: оба замка §3 их не держали (публикаций нет, а `health_state='keep'` человек не успевает поставить за 20 минут). Поэтому у уборщика пауза по инварианту 1 ставится **ТОЛЬКО ВМЕСТЕ с `health_state='keep'`, одним UPDATE**, без окна между запросами; прежнее `health_state` уходит в `health_note`. Разрешение на замену — решение начальника (`health_state=NULL`), и уборщик его уважает.
   **Дыра, которую это открыло:** замок §3 читает `health_state='keep'`, а `accheck.cjs` не держит `'keep'` в своём `KEEP_STATE` — на живом акке очередной чек перепишет замок на `ok`/`defect` и молча снимет защиту. Пока не исправлено в `accheck`, уборщик восстанавливает замок каждый круг (проверка C11), но **только** если на его месте оказался косметический вердикт чека; снятое рукой начальника не возвращает.
   **И главное, что выяснилось следом (см. врезку в §3):** замка нет не только в `accheck` — его нет в ПРОДЕ вообще, оба замка не задеплоены, и `keep` не спас ни одного из четырёх акков. Поэтому у уборщика починка инварианта 1 не безусловная: **проверка C0 каждый круг спрашивает факт — снесён ли за неделю хоть один акк с `keep`.** Снесён = замка нет = паузу не ставим, пишем начальнику. Обход только явным `JANITOR_PAUSE_TERMINAL=1`. Это единственная «починка», которую уборщик умеет отключать сам, потому что она единственная может стоить аккаунта.
4. **Не ставит задачи публикации.** Дыру ретраев (`approved` со слотом в прошлом без задачи) он ПОКАЗЫВАЕТ вместе со справкой `postguard.snapshot`, но задачу не создаёт: постановка разрешена только через `canPost` (инвариант 8) и это уже действие, а не уборка.
5. **Молчит в телеграме.** Приказ «выключи эту хуету»: находки идут в отчёт-файл (`/tmp/accjanitor/last.txt`) и в `account_events` (`kind` = `janitor_fix` | `janitor_login` | `janitor_lap`). Канал есть, включается `JANITOR_TG=1`, и уходит только короткая сводка.
6. **Безопасная починка = три вещи и ничего больше:** поля базы по §3, имена профилей GoLogin, снятие зависших задач и фиксация исходов постов. Всё, что требует входа, в отчёте помечается «нужен вход» с готовой командой.
7. **Сухой прогон обязан быть сухим.** Поэтому в режиме без `--fix` не зовётся ни `canPost` (он попутно подметает задачи), ни `accheck` (он платный и пишет в базу) — вместо них `postguard.snapshot` (только чтение) и сохранённые вердикты.
8. **Синглтон — файл + `ps`, а не `pgrep -f`.** В `runners3.sh` сторож написан как `pgrep -f "RUNNER_ID=$N node localrunner.cjs"` и не срабатывает НИКОГДА: присваивание переменной окружения делает шелл, в argv его нет. У уборщика два замка: `/tmp/accjanitor.lock` (круг, атомарный `wx` + проверка владельца через `ps -o command=`) и `/tmp/accjanitorloop.lock` (цикл, атомарный `mkdir`). Мёртвый владелец → замок снимается сам, иначе один аварийный выход выключает автономность навсегда.

## 10. ЛОКАЛЬНЫЙ РАННЕР И ЕГО СТОРОЖ (07.08) — очередь публикаций не имеет права стоять молча

**Повод.** Третий случай за неделю: посты раздали на аккаунты, задачи легли в `local_jobs` со
статусом `queued`, `localrunner.cjs` был жив по `ps`, лог не двигался 40 минут, очередь не
разбиралась. Помогло только ручное убийство процесса.

**Корень.** Работа с базой без таймаутов. `pg.Client` создавался без `connectionTimeoutMillis` и
`query_timeout`, то есть `await c.connect()` и `await c.query()` ждали ответа БЕСКОНЕЧНО, а без
`keepAlive` полуоткрытое соединение (Railway рвёт их регулярно) выглядит для процесса как «ответ
сейчас придёт». Главный цикл `for(;;)` стоял на этом `await` навсегда: процесс жив, событий нет,
лога нет. Ошибку опроса при этом глушил пустой `catch`, а обработчика `'error'` на клиенте не было
(в node-pg это отдельный способ умереть без объяснений).

**Что теперь обязательно для ЛЮБОГО процесса, который ходит в эту базу из .cjs:**
- клиент только с `connectionTimeoutMillis`, `query_timeout`, `statement_timeout` и `keepAlive`;
- слушатель `client.on('error')` есть всегда: без него обрыв соединения = смерть процесса;
- соединение пересоздаётся на каждом круге и НЕ держится открытым во время долгой работы;
- ошибка базы печатается в лог с причиной, а не глушится (иначе снаружи «встало молча»).

**Сердцебиение.** Раннер раз в 5 минут пишет строку в лог, метку в файл `/tmp/localrunner.beat` и
строку в таблицу `runner_heartbeat` (§4, владеет `schema.sql`). Ключевое поле не `beat_at`, а
**`tick_at` — время последнего УСПЕШНОГО опроса очереди**: у зависшего на запросе процесса таймер
сердца продолжает тикать, и только застывший `tick_at` отличает зависание от нормального простоя.
Заодно на каждом ударе подметаются задачи, застрявшие в `running` (`postguard.reapStale` для
`igpost` плюс остальные режимы в самом раннере): раньше `reapStale` звался ТОЛЬКО из `canPost`, и
если раннер лежал, зависшая задача блокировала аккаунт по уникальному индексу вечно.

**Сторож `runnerguard.sh`.** Круг раз в минуту, судит по ФАКТУ работы, а не по `ps` и не по mtime
лога (оба врут: раннер молчит в логе и когда нормально публикует). Перезапускает, если: метки нет
при живом процессе, сердце молчит >13 мин, задача идёт >30 мин (таймаут самого раннера 20), или
`tick_at` старше 10 мин. Если база не отвечает и раннеру, и сторожу, не перезапускает никого, а
пишет «это не он». Держит РОВНО ОДИН раннер (CONC=1): лишние гасит по одному pid. Гасит только по
pid и только процессы, у которых в командной строке `localrunner.cjs`; **`pkill` по шаблонам
запрещён** (прежняя версия сторожа `pkill -f "node localrunner.cjs"` убивала все раннеры сразу).
Orbita и профили GoLogin не трогает никогда. Дочернего публикатора при гашении раннера НЕ убивает:
`igpost2` сам закрывает окно и сам пишет `external_url`, а прерванный на середине даёт дубль в ленте.

Запуск: `cd /Users/qq/Desktop/neironka-poster && nohup ./runnerguard.sh >/dev/null 2>&1 &`
(лог `/tmp/runnerguard.log`, осмотр без действий `GUARD_DRY=1`). Проверка конвейера без живых
аккаунтов: задача `mode='ping'` (раннер держит её `n` секунд и отвечает) плюс `RUNNER_MODES=ping`,
чтобы приёмочный раннер не мог взять настоящую публикацию. `runners3.sh` (три раннера) с этим
сторожем несовместим: лишних он погасит.
