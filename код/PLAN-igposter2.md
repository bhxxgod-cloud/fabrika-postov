## Схема прогона публикатора (igpost2.cjs)

1. Гейты до браузера: post approved + не post_submitted; media_url скачан (файл, размер >0); акк live + куки есть. Не прошёл — пост queued/failed с причиной, окно НЕ открываем.
2. startLocal (Orbita, локально). GoLogin 503 → ретрай с паузой, задача остаётся queued (до post_submitted ретраи безопасны).
3. Подставили куки → classifyScreen. Вердикт logged подтверждаем принадлежность: кука `ds_user_id` == сохранённый user_id акка (колонку завести, снимать при съёме кук). Чужой id = стоп, это «1 модель = 1 аккаунт» на уровне инварианта.
4. Снять текущий список shortcode с профиля (база для проверки успеха).
5. Создание поста: только кликом «New post» + ЖДЁМ create-dialog (положительный признак: dialog + input[type=file]). Прямой /create/select/ не работает (редирект, факт 29.07).
6. Файл → crop 9:16 → шаги Next, НО перед поиском Share положительно подтверждаем экран подписи (видимое caption-поле). Ввод подписи через visEdit + обратное чтение.
7. `post_submitted=true` → клик Share (после этого ретраи запрещены НАВСЕГДА, инвариант старый).
8. Успех = новый shortcode на профиле (до 3 мин опроса). Появился → published + external_url + первый коммент со ссылкой (через visEdit). Не появился → status `ambiguous` (НЕ failed, ретраев нет) + алерт с двумя скринами.
9. Пересъём кук → в БД. Закрыть окно (stopLocal + kill, как в igpost).

## Ретрай-политика (одна на всё)

- До `post_submitted=true`: любые провалы = задача queued, можно повторять (скачивание, 503, окно, диалог).
- После: никогда. `ambiguous` разруливается только глазами/сторожем.

## Автономность (после ручной обкатки)

- Автопуш в local_jobs: web-панель сама ставит igpost, когда post approved + scheduled_at наступил + акк live (публикует всё равно мак).
- Сторож раннера: posts queued > 30 мин при молчащем localrunner → алерт.
- ТГ-увед типа «результат»: опубликовано/провал по каждой модели.

## Фиксация исхода публикации (добавлено 06.08 после дубля в ленте)

Ошибка №10 («успех = новый shortcode») была реализована, но исход этот НЕ ДОЕЗЖАЛ до базы, и это
оказалось отдельной, более дорогой ошибкой: пост залит, `external_url` пуст, материал заливают
повторно. Так в ленте @darya.smirnova13 повисли DbrPpFowqZk и Dbrbnu5BbLN — один и тот же пост.

Разбор корня: «второе мнение снаружи» звало `before.includes(...)`, где `before` — это Set из
`iglib.getShortcodes`. У Set нет `includes` → TypeError → молчаливый `catch {}` → внешняя проверка
ВСЕГДА отвечала «не видно». Ни одного успешного подтверждения снаружи за всё время работы.

Конструкция, которая это закрывает:

| Дыра | Решение |
|---|---|
| Внешняя проверка молча падала | `postverify.cjs`: единый модуль сверки без браузера, три источника (кука акка через свой прокси → аноним → аноним через прокси), исход всегда объект с причиной, ошибки видны в логе |
| «Не видно» путали с «не опубликован» | `readFeed()` различает `{ok:true}` / `{ok:false, why}` / `{ok:false, gone}`. Пустая лента считается фактом только у профиля, который читается и говорит «постов 0» |
| Смерть процесса между Share и записью | Улика в `posts.meta.share_click` ставится ДО клика: время + список роликов «до». По ней исход восстанавливается позже |
| База не приняла запись исхода | 4 попытки записи, затем улика на диск `/tmp/igpost2_unsaved/<post_id>.json` |
| Зависшие посты копились без разбора | `postreconcile.cjs`: сверка ленты с базой, дописывает ссылку или закрывает `failed`; сухой прогон по умолчанию, запись по `--apply` |
| Совпадение по подписи ≠ наш пост | Отбрасываем ролики, занятые другим постом, попавшие в `before` и снятые раньше создания поста (на @bryan436344 три поста с одной подписью) |

Инвариант «после Share ретраев нет» не менялся: чинили фиксацию исхода, а не право на повтор.
